# Previous track

The Previous track control is available in the full and compact player controls and through Media Session `previoustrack`. It loads a prior server-owned occurrence at its configured `startAt` (or zero), preserving the room's playing/paused state and resetting speed to 1. It never seeks the local provider or interprets a client-supplied undo event.

- Previous requires `playback.skip` and an established authoritative playback session. It is unavailable when vote-skip is enabled, including for owners, so it cannot bypass the room's voting policy. Rewind remains a separate seek control.
- Each accepted Previous walks one occurrence backwards. An empty back stack disables the control and returns `unavailable` without changing playback. It can restore the last occurrence after natural queue exhaustion; the room remains paused after exhaustion.
- Natural advances and completed skips contribute to navigation history. A pending skip vote contributes nothing. History survives queue edits and mode changes; it is not a reset of the queue or playback log.
- Legacy queues retain up to 100 prior occurrences in their private Redis room snapshot. Previous puts the interrupted current item at the queue head for Next in Manual, Vote and Loop modes. Existing Loop requeue behavior remains intact. DJ mode keeps its repeat-current Next behavior, so Previous does not enqueue the interrupted item there. Legacy play-now transitions are also remembered.
- Music keeps bounded past/future cursors (100 each) in its transactional SQL snapshot. Previous retains the interrupted occurrence ahead of the scheduled queue. Next and natural completion follow that return path first, then resume the published scheduler plan. Queue previews, totals and pagination include this return path; users with queue removal permission can remove a return-path entry without deleting playback history.
- Music resolves historical catalogue IDs again and checks current source availability, local source authorization, contributor presence policy and mood rules. Manual tracks reuse only their existing server-issued confirmations. If the immediate historical target is no longer eligible, Previous fails without consuming it or replacing the current track; it does not silently skip backward over it.
- Replayed Music occurrences reuse their original `playbackId` and start accounting. They produce fresh transport occurrences but no duplicate contribution debit, request consumption, recency event or overwrite of an existing end reason. A paused, unstarted interrupted occurrence remains unstarted until it actually plays. Older Music snapshots derive their initial navigation cursor from existing playback history; no history or scores are cleared.

Previous uses the bounded playback command receipt mechanism, live session/membership/permission checks, connection guards, epoch and occurrence guards, plus an exact sequence guard. Empty timelines use occurrence zero with their sequence, preventing a delayed empty-state command from acting after a later track ends. Duplicate request IDs return the original receipt; changed payloads conflict. Music changes install and publish only after the guarded SQL transaction commits. There is no legacy protocol fallback for Previous.

Legacy navigation expires with its Redis room snapshot. Music navigation is durable with SQL room state. This feature does not change existing legacy undo behavior or add Music votes for Previous.
